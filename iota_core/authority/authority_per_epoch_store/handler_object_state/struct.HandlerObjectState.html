Struct HandlerObjectState 

Source 
pub struct HandlerObjectState { /* private fields */ }
Expand description

The rows held in memory and the map from transaction key to assigned commit, with every operation that combines them with the table. A row held in memory is removed only after it is written to the table, and reads look in memory first, so a row found in both places reads the same.

Assigns commit index to its roots and hands the commit to the execution watcher. Call it before any of the roots can be scheduled for execution.

§Panics

If commit index is already assigned. A second call would let the watcher drop map entries of roots it never awaited, and only a bug in the consensus handler processes a commit twice on one epoch store.

pub async fn wait_for_fully_executed_commit(&self, index: CommitIndex)

Waits until commit index and everything below it is fully executed, returning immediately when that already holds. The caller bounds the wait with within_alive_epoch: at epoch end the last commits may never complete.

§Panics

If the commit is not fully executed and the execution watcher has stopped on an error. The commit would then complete only through a flush, which needs its checkpoint certified with signatures carried by commits the caller has not processed. Release builds abort on any panic, so this stops the node. Builds that unwind, such as tests and the simulator, stop only the caller’s task, the consensus handler, unless CRASH_ON_PANIC is set. A restart of the process re-seeds the highest fully executed commit from the resume point.

pub fn record_executed_transaction( &self, key: &TransactionKey, effects: &TransactionEffects, ) -> bool

Puts one executed transaction’s rows in memory if the handler has assigned its commit, and returns whether it had. Call it before the transaction’s outputs become readable, so no object is ever readable without its row.

key is the executed transaction’s TransactionKey, the key the handler assigned. A randomness state update is assigned under its randomness round, so its digest would not be found.

Source

pub fn record_commit_fully_executed( &self, index: CommitIndex, upserts: &[(ObjectKey, HandlerProcessedObject)], inserts: &[(ObjectKey, HandlerProcessedObject)], )

Marks commit index fully executed: puts the commit’s rows in memory, keeps their keys for the commit’s flush (Self::take_completed_commit_rows), and removes the commit’s map entries.

upserts are all the commit’s rows, and inserts the ones Self::rows_not_yet_present returned for them. Only inserts are put in memory. A row already present is in memory or in the table with the same value, and putting it in memory again would make the commit’s flush write a row a second time after the checkpoint executor already wrote it in its own batch. The keys kept for the flush cover all of upserts.

Does nothing once the quarantine flush has completed the commit: its rows are in the table already, and rows put in memory now would never be removed. The caller holds the quarantine lock, so the flush cannot complete the commit between that check and the insert.

Source

pub fn rows_not_yet_present( &self, tables: &AuthorityEpochTables, upserts: &[(ObjectKey, HandlerProcessedObject)], ) -> IotaResult<Vec<(ObjectKey, HandlerProcessedObject)>>

The rows of upserts with no row yet at their key, in memory, in the read-through cache or in the table. Unlike Self::handler_processed_object, a row found in the table is not added to the cache, since no validation is about to read it.

Source

pub fn complete_commit_at_flush( &self, index: CommitIndex, rows: &[(ObjectKey, HandlerProcessedObject)], )

Completes commit index from the quarantine flush, when the flush reaches it before the execution watcher does, as in a replay after a restart. Does nothing once the watcher has completed it.

Like Self::record_commit_fully_executed, this puts rows in memory and removes the commit’s map entries. The caller writes rows with Self::write_commit_rows_to_batch right after, and passes the same rows to Self::evict_flushed_commit_rows once that batch is written. That call, not this one, raises the highest fully executed commit.

Source

pub fn take_completed_commit_rows( &self, index: CommitIndex, ) -> Option<Vec<(ObjectKey, HandlerProcessedObject)>>

Returns the rows the flush of commit index must write: the commit’s rows still held in memory. Returns None if the execution watcher has not completed the commit. The flush then derives the rows from effects and calls Self::complete_commit_at_flush.

Also forgets the row keys of this commit and of every earlier one, so call it only from the commit’s flush.

A row of the commit that is not held in memory is not an error: the checkpoint executor already wrote it to the table and removed it from memory.

Source

pub fn handler_processed_object( &self, tables: &AuthorityEpochTables, key: &ObjectKey, ) -> IotaResult<Option<HandlerProcessedObject>>

The row at key, from memory, the read-through cache or the table.

Returns the row whatever commit produced it. A caller validating at commit C must treat a row produced above C - K as missing.

Source

pub fn highest_handler_processed_row( &self, tables: &AuthorityEpochTables, id: &ObjectId, ) -> IotaResult<Option<(ObjectKey, HandlerProcessedObject)>>

The row of id at its highest version, from memory or the table, whichever holds the higher version. A key present in both holds the same row. Like Self::handler_processed_object, it returns the row whatever commit produced it.

The read-through cache is not used, here or in Self::lowest_handler_processed_row_above: it is keyed by exact version, so it cannot tell which versions of id have a row.

Source

pub fn lowest_handler_processed_row_above( &self, tables: &AuthorityEpochTables, id: &ObjectId, version: Version, ) -> IotaResult<Option<(ObjectKey, HandlerProcessedObject)>>

The row of id at its lowest version above version, from memory or the table, whichever holds the lower version. A key present in both holds the same row. Returns the row whatever commit produced it and, like Self::highest_handler_processed_row, does not use the read-through cache.

Source

pub fn highest_handler_processed_row_below( &self, tables: &AuthorityEpochTables, id: &ObjectId, version: Version, ) -> IotaResult<Option<(ObjectKey, HandlerProcessedObject)>>

The row of id at its highest version below version, from memory or the table, whichever holds the higher version. A key present in both holds the same row. Returns the row whatever commit produced it and, like Self::highest_handler_processed_row, does not use the read-through cache.

A caller walking down from the highest row to find the version live as of commit C - K relies on the versions of id rising with produced_at. That holds for an object that changes only through a shared parent, such as a dynamic field of the coin deny list: its versions are assigned in the order of the commits that change it.

Source

pub fn write_commit_rows_to_batch( &self, tables: &AuthorityEpochTables, batch: &mut DBBatch, handler_rows: &[(ObjectKey, HandlerProcessedObject)], ) -> IotaResult

Stages a commit’s rows into batch, the batch of the quarantine flush of the commit’s output, which also writes last_consensus_stats. After the batch is written, and not before, pass the same commit index and rows to Self::evict_flushed_commit_rows.

Rows are keyed per version, so flushes of different commits may be written in any order without one overwriting another.

Source

pub fn evict_flushed_commit_rows( &self, commit_index: CommitIndex, handler_rows: &[(ObjectKey, HandlerProcessedObject)], )

Removes a commit’s rows from memory. Call it only after the batch from Self::write_commit_rows_to_batch is written, so a concurrent read always finds each row in memory or in the table.

A flushed commit’s checkpoint has executed, so this also raises the highest fully executed commit.

Source

pub fn checkpoint_rows<'a>( &self, effects: impl IntoIterator<Item = &'a TransactionEffects>, ) -> Vec<(ObjectKey, HandlerProcessedObject)>

The rows the executions behind effects put in memory, at every key Self::record_executed_transaction could have written. effects are the transactions of one checkpoint whose outputs are not written yet.

Source

pub fn write_checkpoint_rows_to_batch( &self, tables: &AuthorityEpochTables, batch: &mut DBBatch, rows: &[(ObjectKey, HandlerProcessedObject)], ) -> IotaResult

Stages a checkpoint’s rows into batch, a separate batch the checkpoint executor writes just before the checkpoint’s outputs. After the batch is written, and not before, pass the same rows to Self::evict_flushed_checkpoint_rows. Rows never change once written for a key, so checkpoints may write in any order and concurrently with a commit’s flush.

Source

pub fn evict_flushed_checkpoint_rows( &self, rows: &[(ObjectKey, HandlerProcessedObject)], )

Removes a checkpoint’s rows from memory. Call it only after the batch from Self::write_checkpoint_rows_to_batch is written.

After a crash, executing the checkpoint again puts the same rows in memory again, and calling this for that execution removes them.
