Module handler_object_state

The handler object state: the object versions that the commits assigned by the consensus handler produce, kept per epoch for P-COOL deterministic post-consensus validation. Validation reads object state as of a commit from it, however far local execution has got.

Terms used here:

  • C is the commit being validated, and K is how many commits behind C validation reads the object state: the protocol config’s pcool_deterministic_validation_horizon_distance. Validation at C reads the state as of commit C - K, called the horizon.
  • A row is one entry of the handler object state. It records that a transaction in some commit produced version V of object id: the commit, the digest, and whether the object is live, deleted or wrapped at that version. “The row at (id, V)” is that entry. Rows are read at the exact version a transaction names or, for a shared object that is gone, at the object’s highest version.
  • Rows are written to the epoch table handler_processed_objects. Until then they are held in memory. A row held in memory is removed only after it is written to the table, and reads look in memory first.
  • The roots of a commit are the keys of the transactions the handler put in the commit’s pending checkpoints, cancelled transactions included.
  • A commit is fully executed when every root of it has effects.
  • The execution watcher is the task that waits for the effects of the roots of each assigned commit and then marks the commit fully executed (ExecutionWatcher in the consensus handler).
  • The resume point is the last commit whose output the quarantine flush wrote. After a restart the handler replays the commits above it.

On a committee validator every execution belongs to a commit the handler has assigned: the checkpoint executor runs a transaction only after the handler has assigned its commit, until the node switches to executing synced checkpoints for the rest of the epoch, which stops the handler. The change-epoch transaction and genesis run outside any commit and write no rows. What they write is the state the next epoch starts with.

HandlerObjectState owns the rows held in memory and the map from transaction key to assigned commit.

The rows and the map change at these points:

  • the handler assigns a commit to its roots before any of them can be scheduled (HandlerObjectState::assign_commit_to_transactions, through the epoch store);
  • each execution of a transaction whose commit is assigned puts its rows in memory before its outputs become readable (HandlerObjectState::record_executed_transaction);
  • a commit is completed, either by the execution watcher once it is fully executed (HandlerObjectState::record_commit_fully_executed) or by the quarantine flush of its output when that comes first (HandlerObjectState::complete_commit_at_flush). Either way the commit’s rows are put in memory, skipping the rows already present, and the commit’s keys are removed from the map;
  • the execution watcher stops on an error (HandlerObjectState::record_execution_watcher_error). After that only a flush completes a commit, and a wait for a commit that is not fully executed panics;
  • rows are removed from memory once they are written to the table.

Completing a commit also raises the highest fully executed commit (HandlerObjectState::wait_for_fully_executed_commit). Validation of a commit waits on it, so that it reads rows no execution can still add to.

Rows are written to the table at two points:

  • the quarantine flush of a commit’s output, once its checkpoint is certified and executed, writes the commit’s rows not yet in the table, in the same batch as last_consensus_stats (HandlerObjectState::write_commit_rows_to_batch). For a commit the execution watcher completed, these are its rows still held in memory (HandlerObjectState::take_completed_commit_rows). Otherwise they are all the commit’s rows, derived from its effects;
  • for every executed checkpoint, the checkpoint executor writes the rows its executions put in memory, in a separate batch written just before the checkpoint’s outputs and its watermark (HandlerObjectState::write_checkpoint_rows_to_batch). So an object is never written without its row. Rows never change once written for a key, so this batch takes no lock.

Neither batch is synced to disk when written, so the order of these writes holds across a process crash but not across a power loss or kernel crash.

A deleted shared object’s row keeps its initial shared version, taken from the consumed input’s owner, and every Deleted row names the transaction.
handler_rows_for_commit
The rows a commit’s executed transactions produce. The execution watcher and the quarantine flush both derive a commit’s rows here, so they always agree.
