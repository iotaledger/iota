4//! Reads the inputs of a transaction for post-consensus validation as of a
5//! consensus commit, so that every validator reaches the same result,
6//! however far its own execution has got. It also reads a dynamic field as
7//! of the horizon for the deny checks at the commit: a field of the coin deny
8//! list, or an account's authenticator function field. That read answers
9//! present or absent, not keep, drop or missing.
10//!
11//! Terms used here and in the submodules:
12//! - `C` is the commit being validated.
13//! - `K` is how many commits behind `C` the object state is read: the protocol config's
14//!   `pcool_deterministic_validation_horizon_distance`. Validation at `C` reads the state as of
15//!   commit `C - K`, called the horizon. Every validator has executed the commits at or below the
16//!   horizon before it validates `C`, while a commit above the horizon may be executed on some
17//!   validators and not yet on others.
18//! - A row is one entry of the handler object state (`handler_object_state`). It records that a
19//!   transaction in some commit produced version `V` of object `id`: the commit, the digest, and
20//!   whether the object is live, deleted or wrapped at that version. "The row at `(id, V)`" is that
21//!   entry for the version a transaction names.
22//! - The store is this validator's object store, read through the execution cache.
23//!
24//! Each input gets one of three results:
25//! - keep: the input is valid as of the horizon, and the transaction goes on to the other checks;
26//! - drop: the input can never become valid (the version is already consumed, the digest or the
27//!   owner is wrong), so the transaction is dropped;
28//! - missing: the input is not visible as of the horizon, but a later commit may still produce it,
29//!   so validation at `C` cannot decide it yet.
30//!
31//! Owned, shared and package inputs each have their own submodule. Each
32//! reads in a fixed order of steps, and each step is its own type that offers
33//! only the next allowed read, so a read cannot be skipped, repeated or taken
34//! out of order.
35//!
36//! On a validator that keeps the handler object state, every transaction
37//! executed this epoch belongs to a commit the consensus handler has
38//! assigned, so every object written this epoch has a row, and the row is
39//! written before the object reaches the store. The only executions without
40//! a row are the change-epoch transaction and genesis, whose writes are the
41//! state the epoch starts with, and synced checkpoints executed after the
42//! handler has stopped for the rest of the epoch, when no validation runs
43//! any more.
44//!
45//! # Why the store answer for an id with no row is the epoch-start state
46//!
47//! When the row they look for does not exist, the owned and shared readers
48//! ask the store. For an id with no row at all, that answer gives the same
49//! result on every validator, for the three reasons below, with one exception
50//! given in point 3.
51//!
52//! 1. Every write this epoch leaves its row before its object, so the store is never ahead of the
53//!    rows for an id.
54//! 2. The rows are kept per epoch and start empty. An id with no row has not been written this
55//!    epoch on this validator, so the store holds the version the epoch started with, and every
56//!    validator starts the epoch with the same state. A shared object is the exception: its
57//!    mutations write no rows, so the store can hold a later version of it, with the same owner.
58//! 3. The pruner removes only older versions that a newer one replaced, so the latest version of a
59//!    live object stays. A deleted or wrapped object is the exception: pruning the checkpoint that
60//!    deleted or wrapped it removes its tombstone too, so for an object deleted or wrapped in an
61//!    earlier epoch some validators find the tombstone and others find nothing. The owned reader
62//!    then drops the input on a validator that still has the tombstone and answers missing on one
63//!    that pruned it. Both leave the transaction out of the commit, but the error reported differs
64//!    (final or retryable). The shared reader, which reads only live objects, finds nothing in
65//!    both.
66//!
67//! An id can have rows at other versions than the one a reader looks for.
68//! Rows at or below the horizon are on every validator, but a row above the
69//! horizon is only on the validators that executed its commit, and their
70//! store already shows that write. So a reader decides from such a store
71//! answer only after reading the other rows of the id, and answers as a
72//! validator that has not executed any commit above the horizon would: the
73//! owned reader from the lowest row of the id above the named version, the
74//! shared reader by checking a drop against the lowest row of the id. The
75//! owned and shared modules explain the rules. Mutations of a shared object
76//! write no rows, so a shared object named as owned is decided from its
77//! creation row, not from its version.
78//!
79//! After the store answer, the row is read once more. This covers a write
80//! that lands between the first row read and the store read. Such a write
81//! put its row in place before its object (point 1), and a row stays
82//! readable once written (a row held in memory is removed only after it is
83//! written to the table), so the second read finds the row, and the row
84//! decides.
85//!
86//! A write that lands after the store read belongs to a commit above the
87//! horizon, because validation at `C` starts only once every commit at or
88//! below the horizon is executed. If the second read sees that write's row,
89//! the row answers missing. If it does not, the store answer is the state
90//! that every validator which has not executed that commit also sees. So one
91//! more read is enough, and a third would only face the same window again.
92//!
93//! # Loading the object of a kept version
94//!
95//! A kept owned input is loaded by exact key, and this validator may already
96//! have consumed that version. A version consumed by a commit at or below the
97//! horizon drops, from the consuming commit's row, before any load. A version
98//! consumed above the horizon is kept, as on a validator that has not
99//! executed that commit, unless the consuming transaction holds a lock that
100//! the lock conflict check finds first. That holds for a version the epoch
101//! started with too: a newer version in the store does not drop it by
102//! itself, as the owned module explains. The object of such a version,
103//! including one consumed without a lock as a received object or a
104//! dynamic-field child, stays in the store, because the objects pruner does
105//! not pass the pruning limit, which covers every commit that a validation,
106//! or a replay after a restart, can still read (see
107//! `AuthorityPerEpochStore::object_pruning_limit`). A kept version missing
108//! from the store is therefore a storage error.
109//!
110//! # Dynamic fields as of the horizon
111//!
112//! The dynamic field reader walks down from a field's highest row to the
113//! highest one at or below the horizon. That needs the field's versions to
114//! rise with the commits that change it, which holds for a field that changes
115//! only through its shared parent object, so in the order of the commits that
116//! change it. The fields of the coin deny list change only through the
117//! shared deny list object, and an account's authenticator function field
118//! only through the shared account. A field with no row reads the store and
119//! then the rows again, as explained under "Why the store answer for an id
120//! with no row is the epoch-start state" above.
121//!
122//! The coin deny check also needs the type of a kept shared input, whose
123//! object the shared reader does not read. That read takes the latest store
124//! object even when rows exist, because an object's type never changes, and
125//! once the object is gone, the version its deletion replaced.

145/// The reader's result for one owned or immutable input. The module doc
146/// says what keep, drop and missing mean.

149    Keep(KeptObject),
150    Drop(DropReason),
151    Missing(MissingReason),
152}

154/// The reader's result for one shared input. Only whether the object exists
155/// and is shared at the declared initial version is checked, never its
156/// contents.
157#[must_use]
158pub enum SharedVerdict {
159    /// Live and shared at the declared initial version. Holds no object:
160    /// execution reads it at the version consensus assigns.
161    Exists,
162    /// Deleted by a commit above the horizon. The input is kept and passed
163    /// on as `DeletedSharedObject`, with the version and the deleting
164    /// transaction from the tombstone row. Neither decides anything at the
165    /// commit.
166    Deleted(Version, TransactionDigest),
167    Drop(DropReason),
168    Missing(MissingReason),
169}

174pub enum PackageVerdict {

231/// Which read decided a drop. `V` is the version the transaction names.
232#[derive(Clone, Copy, Debug, PartialEq, Eq)]
233pub enum DropKind {
234    /// The row at `(id, V)` is a tombstone: the object was deleted or
235    /// wrapped at that version.
236    HandlerRowTombstone,
237    /// The row at `(id, V)` is live, with another digest.
238    HandlerRowDigestMismatch,
239    /// A row of `id` at a version above `V`, produced at or below the horizon:
240    /// a commit every validator has executed consumed `V`.
241    HandlerRowSuperseded,
242    /// The row at `(id, V)` is a shared object's creation row, but the
243    /// transaction names the object as owned.
244    HandlerRowSharedObject,
245    /// No row at `(id, V)`, and `V` was replaced before this epoch: the store
246    /// holds a newer version or a tombstone, and the lowest row of `id` above
247    /// `V`, if there is one, replaced another version.
248    StoreSuperseded,
249    /// No row at `(id, V)`, and the store's object at `V` has another digest:
250    /// as the latest reference, or as the object loaded for a kept input.
251    StoreDigestMismatch,
252    /// Named as owned, but the id is a shared object created at or below the
253    /// horizon or before the epoch.
254    SharedObjectNamedAsOwned,
255    /// Named as shared, but the row or the store object is not shared at the
256    /// declared initial version.
257    SharedNotCreatedShared,
258    /// Shared at another initial version than declared.
259    SharedInitialVersionMismatch,
260    /// A shared object deleted by a commit at or below the horizon.
261    SharedDeletedAtOrBelowHorizon,
262}

264/// Which read decided a missing. `V` is the version the transaction names.
265#[derive(Clone, Copy, Debug, PartialEq, Eq)]
266pub enum MissingKind {
267    /// The row at `(id, V)` was produced above the horizon.
268    HandlerRowAboveHorizon,
269    /// No row, and the store's latest reference is below `V`: this validator
270    /// has not produced the version yet.
271    StoreBelowVersion,
272    /// No row at `(id, V)`, and the store has nothing for `id`.
273    StoreNotFound,
274    /// No row at `(id, V)`, and the store's latest entry for `id` is a
275    /// tombstone left by wrapping.
276    StoreWrapped,
277    /// No row at `(id, V)`, and a row of `id` above the horizon shows that at
278    /// the horizon `id` was live at a version below `V`, or not live.
279    VersionNotLiveAtHorizon,
280    /// The shared object's creation row was produced above the horizon.
281    SharedCreationAboveHorizon,
282    /// No creation row, the store has no live object and no row shows a
283    /// deletion.
284    SharedNotFound,
285    /// The package is not in the store.
286    PackageNotFound,
287    /// The package's row was produced above the horizon.
288    PackageAboveHorizon,
289    /// A Move authenticator's account had no authenticator function field at
290    /// the horizon: it was not an account yet, or never became one.
291    AuthenticatorFunctionNotFound,
292}

294/// The loader's result for one transaction's inputs at a commit. `Loaded`
295/// holds every input as the input checks expect it. Receiving objects are
296/// read separately, see [`ReceivingObjectsResolution`]. `Drop` and `Missing`
297/// name the first input that decided. A missing input is not an error, so
298/// the caller must handle it rather than turn it into one.
299#[must_use]
300pub enum InputResolution {
301    Loaded(InputObjects),
302    Drop(InputObjectKind, DropReason),
303    Missing(InputObjectKind, MissingReason),
304}
305
306/// The loader's answer for one transaction's receiving objects at a commit.
307/// `Loaded` holds every one as the existing receiving checks expect it. The
308/// other two name the first reference that decided, under its owned kind.
309#[must_use]
310pub enum ReceivingObjectsResolution {
311    Loaded(ReceivingObjects),
312    Drop(InputObjectKind, DropReason),
313    Missing(InputObjectKind, MissingReason),
314}

316/// One transaction's inputs for validation at a commit, grouped as the input
317/// checks take them, or the first input that dropped or is missing.
318#[must_use]
319pub enum ValidationInputsAtCommit {
320    Loaded {
321        tx_input_objects: InputObjects,
322        tx_receiving_objects: ReceivingObjects,
323        per_authenticator_inputs: Vec<(InputObjects, ObjectReadResult)>,
324    },
325    Drop(InputObjectKind, DropReason),
326    Missing(InputObjectKind, MissingReason),
327}

329/// The result of validating one transaction at a commit. A check after
330/// loading that rejects the transaction returns the same `Err` as at
331/// admission, not a result, except the denial of an authenticator package,
332/// which the caller needs to tell apart from the other errors.
333#[must_use]
334#[derive(Debug)]
335pub enum ValidationAtCommit {
336    /// Every check passed. Holds the owned object references to lock.
337    Keep(Vec<ObjectReference>),
338    Drop(InputObjectKind, DropReason),
339    Missing(InputObjectKind, MissingReason),
340    /// The deny rules deny the package holding an account's authenticate
341    /// function, named by the account's authenticator function field as of
342    /// the horizon. The accounts are the transaction's signers, so every copy
343    /// of the transaction is denied alike.
344    AuthenticatorPackageDenied(IotaError),
345}
