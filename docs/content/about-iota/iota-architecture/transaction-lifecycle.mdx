1.  **Create and Sign a Transaction**: A user creates a transaction using a wallet application. This transaction can affect objects owned by the user, as well as [shared objects](../../developer/iota-101/objects/object-ownership/shared.mdx). The wallet application then signs the transaction with the user's private key.

2.  **Submit to Validators**: The client application communicates with a full node, which then distributes the transaction to all validators following the IOTA protocol. The validators verify the transaction. If valid, the validators sign it and return the signed transaction to the full node.

3.  **Form a Transaction Certificate**: After collecting responses from a supermajority of validators, the client forms a transaction _certificate_. Unlike consensus-based blockchains, IOTA validators are not burdened by needing to propagate signatures or aggregate _certificates_; this is the responsibility of the client or gateway.

4.  **Send the Certificate**: The client sends the assembled _certificate_ back to all validators. The validators verify its validity and acknowledge receipt. If the transaction involves only owned objects, IOTA can process and execute it immediately without waiting for consensus (**fast path consensus**). All _certificates_ are forwarded to the IOTA DAG-based consensus protocol.

5.  **Consensus and Execution**: The IOTA DAG-based consensus protocol eventually produces a total order of _certificates_. Validators verify and execute _certificates_ that involve shared objects.

6.  **Form an Effect Certificate**: Clients can gather responses from a supermajority of validators, assemble them into an effect _certificate_, and use it as proof that the transaction is settled.

7.  **Checkpoints and Reconfiguration**: IOTA forms checkpoints for every consensus commit, which are also used to drive the reconfiguration protocol.

## Understanding the Transaction Lifecycle in IOTA

IOTA transactions undergo multiple steps from initiation to finality. This guide explains the transaction lifecycle, detailing the roles of nodes, transaction validation, and certification.

## 1. Initiating a Transaction
A user or smart contract submits a transaction containing:

- **Sender & recipient addresses**
- **Amount to transfer**
- **Timestamp & nonce**
- **Digital signature**

## 2. Transaction Submission
Once created, the transaction is submitted to an IOTA node. The node:

- Validates the transaction format.
- Checks the sender’s account balance.
- Broadcasts the transaction to other nodes.

## 3. Validation and Inclusion
Full nodes perform consensus checks:

- Ensuring the transaction references valid parent transactions.
- Checking the sender has sufficient funds.
- Validating the digital signature.

If valid, the transaction enters the **mempool** and is broadcast to other nodes.

## 4. Certification and Finalization

Once a transaction enters the mempool, it follows a structured path toward finality:

### 1. Validator Signatures & Effects Certificate

- Validators verify the transaction and sign it.
- The transaction receives an **effects certificate**, which proves that it has been accepted by a quorum of validators.
- This certificate guarantees that the transaction will be included in a checkpoint, meaning it cannot be undone.
- At this stage, the sender and recipient can **reasonably assume the transaction will be finalized**, but it is not yet **fully immutable**.

### 2. Checkpoint Inclusion

- Transactions are grouped into **checkpoints** at regular intervals.
- A checkpoint is a **batch of transactions** that validators collectively confirm.
- Once a transaction is included in a checkpoint, it is permanently recorded on the IOTA network.

### 3. Settlement Finality & Immutability

- **Transaction finality** occurs when the effects certificate is formed, ensuring that the transaction is executed and will be included in a checkpoint.
- **Settlement finality** is reached once a checkpoint is finalized, making the transaction **fully immutable**.

:::info
Finality is achieved once a sufficient number of nodes have certified the transaction.
:::

## Epoch Transitions and Their Impact

The IOTA network undergoes [epoch](./epochs.mdx) changes, which affect transaction processing.

- **Epoch Boundaries & Transaction Resubmission**: If a transaction is submitted near an epoch boundary, it may need resubmission in the new epoch.
- **Who handles resubmission?** Full nodes may need to resubmit transactions in the new epoch. If using a client or wallet app, check if automatic resubmission is implemented.
- **Should users avoid transactions during epoch changes?** While not required, it may help to wait for the epoch transition to complete before submitting time-sensitive transactions.

### Transaction Certificates and Epochs

- **Certificates from the previous epoch become invalid** after an epoch change.
- **What is included in a certificate?** At minimum, the epoch number.
- **How is verification performed?** Validators’ public keys for the relevant epoch must be fetched from the network.
