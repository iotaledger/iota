# Activating DoS Protection for Validators

Validator nodes are critical infrastructure in the IOTA network and should be protected against Denial of Service (DoS) attacks. The TrafficController is a built-in mechanism that helps protect validator nodes by monitoring and limiting traffic from potential attackers.

:::warning

This guide explains how to configure the TrafficController for your validator node.
A node whose configuration has no `policy-config` runs the shipped default policy.
That default runs with `dry-run: true`, thus it only counts and logs the clients it would block.
Set `dry-run: false` to make the node block them, for `connection-blocklist-ttl-sec` seconds each.

:::

## TrafficController Overview

The TrafficController monitors incoming requests to your validator node and can block IP addresses that exceed certain thresholds. It can operate in two modes:

1. **Non-proxy mode** - For validators that receive traffic directly from clients.
2. **Proxy mode** - For validators behind load balancers or proxies.

## Configuration Parameters

The TrafficController is configured through two main configuration structures:

### PolicyConfig

This structure defines the traffic control policies:

```yaml
# The following parameters are defined in the PolicyConfig struct, which controls
# how the TrafficController identifies clients and applies rate limiting policies.
# The struct provides configuration for both direct client connections and proxied
# connections through load balancers.
policy-config:
  # How to identify client IPs (socket-addr or x-forwarded-for)
  client-id-source: socket-addr  # or x-forwarded-for: <hops>, where hops is the number of proxy hops
  
  # Which clients to serve without limits, which to refuse, and what to do with
  # every other client. See "Access Rules" below. Omit the field to rate limit
  # every client.
  access-rules:
    allow: ["203.0.113.7", "198.51.100.0/24"]  # Never counted or blocked
    deny: ["192.0.2.0/24"]  # Refused unless an allow rule matches
    default: limit  # or deny: refuse every client that no allow rule names
    forwarders: ["10.0.0.5"]  # Fullnode only: services that name their users in x-iota-client-ip
  
  # How long to block direct client IPs (in seconds)
  connection-blocklist-ttl-sec: 60
  
  # How long to block proxied client IPs (in seconds)
  proxy-blocklist-ttl-sec: 60
  
  # Policy for handling spam traffic
  spam-policy-type:
    freq-threshold:
      client-threshold: 1000  # Sustained tallies per second per direct client; requests are sampled by spam-sample-rate, so the tolerated request rate is proportionally higher
      proxied-client-threshold: 10  # Sustained tallies per second per proxied client
      burst-secs: 30  # Burst allowance: a client can send client-threshold * burst-secs tallies back to back
  
  # Policy for handling error traffic
  error-policy-type: NoOp  # NoOp, or a freq-threshold map like the spam policy above
  
  # Sampling rate for spam detection (0.0 to 1.0)
  spam-sample-rate: 0.2
  
  # The gas each client may spend on simulations, on a fullnode only. Omit the field for no limit.
  simulation-gas-limit:
    gas-per-sec: 1000000  # How much gas a client's balance refills by each second
    burst-gas: 20000000  # The largest balance a client can save up
  
  # Whether to run in dry-run mode (log but don't block)
  dry-run: false
```

The `burst-secs` key had the name `window-size-secs` before. The node continues to accept the old name, but the old name is deprecated. Change your configuration to `burst-secs`.

## Access Rules

The node decides each request by the first of these steps that matches its client:

1. **`allow`**: the node serves the request. No policy counts the client, and no policy blocks it. Use this for trusted clients, such as your own services or a partner's.
2. **`deny`**: the node refuses the request.
3. **The blocklist**: the node refuses a client that the spam or error policy blocked, or that an operator blocked through the admin API, until its block expires.
4. **`default`**: with `limit` the node serves the request and the policies count it; with `deny` the node refuses it.

A rule is an IP address or a network in CIDR notation, and matches the full address of the client. The node clears the host bits of a network, so `198.51.100.7/24` is the rule `198.51.100.0/24`. A `/128` rule matches one IPv6 address. An IPv4 client can reach the node as an IPv4-mapped IPv6 address. The node matches such a client by its IPv4 address, so IPv4 rules match it. IPv6 rules do not match an IPv4 client. The one exception is an IPv4-mapped rule of `/96` or longer, which the node reads as the IPv4 rule. Write IPv4 rules for IPv4 clients. A request whose client IP the node cannot resolve matches no rule, so the default action decides it.

| Setup | Rules |
| --- | --- |
| Rate limit every client | no rules, `default: limit` (the default) |
| Serve only some clients | `allow` rules, `default: deny` |
| Rate limit every client except trusted ones | `allow` rules, `default: limit` |

An allow rule wins over a deny rule, so a deny rule cannot refuse one address inside an allowed network.

In dry run mode the node serves the requests that steps 2 to 4 refuse, and only counts them. The node logs a warning at startup when it has deny rules or `default: deny` in dry run mode.

The policies count an IPv6 client by the first `ipv6-prefix-len` bits of its address, but the rules match its full address. A client can thus avoid a deny rule longer than `ipv6-prefix-len`: it moves to another address in its own prefix. The node logs a warning at startup for such a rule.

With `client-id-source: x-forwarded-for` the rules match the client that the header names. An allow rule then holds only if clients can reach the node through your proxy alone. A client that reaches the node port directly writes the whole header, and can name an allowed address. The node logs a warning at startup for allow rules with `x-forwarded-for`. It also logs a warning for `default: deny` with `x-forwarded-for`. Under that setting the node refuses every request without the header, because no allow rule can match it. On a validator these are all the requests of the other nodes.

The `allow-list` field is no longer accepted. A node whose configuration sets it to a list refuses to start. Use `allow` rules with `default: deny` instead:

```yaml
policy-config:
  access-rules:
    allow: ["10.0.0.1", "10.0.0.2"]
    default: deny
```

## Simulation Gas Limit

A fullnode simulates transactions for free: gRPC `SimulateTransactions` and `ViewFunctionCalls`, and JSON-RPC `iota_dryRunTransactionBlock`, `iota_devInspectTransactionBlock` and `iota_view`. With `simulation-gas-limit` set, each client has a gas balance that refills by `gas-per-sec` up to `burst-gas`. When a simulation starts, it reserves the computation limit of one transaction (`max_gas_computation_bucket` of the protocol, currently 5,000,000 gas units), or the whole `burst-gas` if that is lower. When it ends, it gets back what it did not use. The node refuses a simulation while the balance of its client is below that reservation, and the refusal says when to retry, in its message and in a field that a client can read: gRPC answers the item with `RESOURCE_EXHAUSTED` and a `RetryInfo` detail, and JSON-RPC answers with the `ServerIsBusy` error code (-32009), `simulation_gas_limit_reached` in `data.reason`, and the seconds in `data.retry_after_secs`. The node still serves the client's other requests, and a refusal does not count toward the error policy. A client is charged its computation cost in gas units, at most the computation limit of one transaction; storage is not charged.

Both values must be above 0. The example values above are not measured defaults. With them, a client can run four simulations back to back that each use the whole computation limit of one transaction. After that, it can run about one every five seconds. Measure what your clients simulate before you set them.

The policies count an IPv6 client by its `ipv6-prefix-len` prefix, and so does the gas limit: the addresses of one prefix share one balance. Clients whose IP the node cannot resolve share one balance. Clients that an allow rule serves have no gas limit. A GraphQL server or an indexer simulates through the fullnode's gRPC API, so all of its users share the balance of its IP, unless the fullnode lists it as a forwarder (see "Trusted Forwarders" below). Do not give either one an allow rule unless the fullnode lists it as a forwarder: simulation through it would then have no limit. For a listed forwarder, an allow rule applies only to the forwarder's own requests, such as the checkpoint reads of an indexer under `default: deny`. It gives the users of the forwarder nothing. In dry run mode the node serves a simulation over the limit, and counts it in `traffic_control_num_dry_run_simulation_gas_refusals`.

The admin API changes the values at runtime. It can turn the limit on for a node whose `policy-config` has no `simulation-gas-limit`, given both values, but it cannot turn the limit off:

```bash
curl -X POST 'http://127.0.0.1:1337/traffic-control?simulation_gas_per_sec=1000000&simulation_burst_gas=20000000'
```

The change lasts until the node restarts. The balances are kept, and cut to a lower `burst-gas` at their next refill.

## Trusted Forwarders

A GraphQL server serves dry runs and view calls, and an indexer serves dry runs, dev inspects and view calls, by calling the gRPC API of a fullnode. For each of these simulations they name the user in the `x-iota-client-ip` header. List them in `access-rules.forwarders` of the fullnode, so that the fullnode treats each user as its own client:

```yaml
policy-config:
  access-rules:
    forwarders: ["10.0.0.5", "10.0.1.0/24"]
```

- A forwarder is an IP address or a CIDR network, written like an access rule.
- GraphQL and the indexer name the user only for these simulations. Their other calls to the fullnode, such as the execution of a transaction, carry no header, so the fullnode counts them for the service itself.
- For a request from a forwarder that carries the header, the fullnode first checks the forwarder itself. A deny rule or a block of the forwarder refuses the request, as it refuses the forwarder's own requests. An allow rule of the forwarder spares it its deny rules and blocks, as for any client. The default action is not part of this check: with `default: deny`, a forwarder needs no allow rule for the requests in which it names a user. Under dry run the fullnode counts the refusal and serves the request. It counts each request once.
- Then the fullnode takes the IP address in the header as the client. The access rules, the blocklist, the spam and error policies and the simulation gas limit apply to that user. The fullnode does not count the request for the forwarder. `traffic_control_forwarded_requests` counts the requests that pass the check of the forwarder.
- An allow rule of the forwarder gives its users nothing: each user goes through the rules on its own. With `default: deny`, the fullnode thus refuses a user that no allow rule names, even when an allow rule names the forwarder.
- To stop a forwarder while the node runs, add a deny rule for it or block it through the admin API. The forwarders themselves change only with the configuration.
- A request from a forwarder without the header, with the header more than once, or with a value that is not an IP address, is the forwarder's own.
- The fullnode ignores the header from every other client.
- The fullnode trusts the header by the IP address of the forwarder alone. With `client-id-source: socket-addr`, the forwarder must connect to the fullnode directly, or through a proxy that keeps the address of the forwarder.
- With `client-id-source: x-forwarded-for`, the forwarders match the client that the `x-forwarded-for` header names, and the node logs a warning at startup. The forwarder must then reach the fullnode through the proxy. A direct connection carries no `x-forwarded-for` header, so the fullnode resolves no client for it and does not treat the request as the forwarder's.
- List only the addresses of the services themselves. Do not list a proxy, a load balancer or a wide network that other clients also pass through. Each of those clients could then name any user in the header, also one that an allow rule serves. So it could escape the simulation gas limit, the access rules and the blocklist.
- GraphQL and the indexer name the address that connects to them. They send it to the fullnode they call, whether or not that fullnode lists them. Behind a load balancer or a proxy, that is the address of the load balancer or the proxy, so all users behind it share one client. Do not give that address an allow rule: simulation through it would then have no limit.
- When the fullnode refuses a call of the indexer (`RESOURCE_EXHAUSTED`), the indexer answers with the `ServerIsBusy` error code (-32009) and the message of the fullnode. This holds for every call of the indexer to the fullnode. GraphQL answers a refused dry run or view call with the code `TOO_MANY_REQUESTS` and the message of the fullnode. For its other calls, such as the execution of a transaction, GraphQL reports a refusal like any other error.
- Validators do not apply `forwarders`, though they still check that each entry is an IP address or a CIDR network.

`iota-tool admin traffic-control rules list` and `GET /traffic-control/rules` show the forwarders. They are set in the configuration only.

## Non-Proxy Mode Configuration

If your validator node receives traffic directly from clients (no proxy or load balancer in front), use this configuration:

```yaml
policy-config:
  client-id-source: socket-addr
  connection-blocklist-ttl-sec: 60
  proxy-blocklist-ttl-sec: 0
  spam-policy-type:
    freq-threshold:
      client-threshold: 100  # Sustained tallies per second
      proxied-client-threshold: 10  # Currently ignored, as proxied client tallies are not reported; 0 would block every proxied client
      burst-secs: 30
  error-policy-type: NoOp
  spam-sample-rate: 0.2
  dry-run: false  # Set to true initially to monitor without blocking
```

## Proxy Mode Configuration

If your validator is behind a load balancer or proxy, use this configuration:

```yaml
policy-config:
  # Configure with the number of proxy hops between client and node
  # For example, if you have one proxy: client -> proxy -> node, use 1
  client-id-source:
    x-forwarded-for: 1  # Adjust based on your infrastructure
  
  connection-blocklist-ttl-sec: 60
  proxy-blocklist-ttl-sec: 60
  spam-policy-type:
    freq-threshold:
      client-threshold: 1000  # Higher threshold for proxies that aggregate traffic
      proxied-client-threshold: 10  # Threshold for individual clients behind proxies
      burst-secs: 30
  error-policy-type: NoOp
  spam-sample-rate: 0.2
  dry-run: false
```

The node reads the entry your proxy appended, so a client cannot hide itself by putting unreadable bytes in the part of the header it sent. A proxy writes only addresses, so the node refuses a request whose selected entry is not valid UTF-8, whatever the policy. It likewise refuses a request whose connection has no peer address. The node still ends up with no client when the header is absent, when the entry it selects is not an address, or when the header holds fewer entries than the configured hop count. With `default: limit` such a request is served and charged to no client, which means it is not rate limited. With `default: deny` it is refused, because it matches no allow rule.

The `traffic_control_unresolved_client_requests` metric counts these requests. On a validator it does not sit at zero: other nodes call the validator directly, their requests carry no header, and each one is counted. Read it as a change from its usual level rather than as an absolute number. A rise above that level means that client traffic reaches the node on another path, or that the configured hop count does not match the number of proxies. On a node that serves clients only, and where every request arrives through the proxy, the metric does sit at zero.

With `default: deny` on a validator, the allow rules have to name every other node that calls it, because those calls arrive on the same listener. Two configurations are possible, and only one of them works. With `client-id-source: socket-addr` the node resolves the address of each caller, so allow rules for the other nodes do admit them, at the cost of rules that have to change with the committee. With `x-forwarded-for` such rules do not help at all: their requests carry no header, the node resolves no address to match against the rules, and the default action refuses them. Prefer to leave `default: deny` off a validator.

### Determining the Correct Number of Hops

While `x-forwarded-for` is set to `0` the node determines no client at all. With `default: limit` that means no client is limited, and with `default: deny` it means every request is refused. Use this setting only to read the hop count off the logs, and set the correct value straight after.

To determine the correct number of hops for the `x-forwarded-for` setting:

1. Set `x-forwarded-for: 0` temporarily.
2. Run the node and query any endpoint from a known IP address.
3. Check the logs for lines containing `x-forwarded-for`.
4. The correct value is 1 + the number of IP addresses that appear after your known IP in the header.

## What if I'm Unsure of the Number of Proxies?

If you're unsure about the correct number of proxies to configure, you can use the [`config-traffic-control.sh`](https://github.com/iotaledger/iota/blob/develop/setups/validator/config-traffic-control.sh) script included in the IOTA codebase. This script analyzes your node logs to determine the correct configuration.

Follow these steps:

1. Configure `x-forwarded-for` in the policy config to `0`, which is a special case setting that allows the node to provide logging details of the `x-forwarded-for` header contents:

```yaml
policy-config:
  client-id-source:
    x-forwarded-for: 0
```

2. Restart your node.
3. Tail the node logs and pipe them into the script, providing as an additional argument an IP address of a known host that you can use to query any endpoint of your validator:

```bash
journalctl -fu iota-node | setups/validator/config-traffic-control.sh "YOUR_KNOWN_IP_ADDRESS"
```

4. Using the host whose IP was provided to the script, query any endpoint of your validator. The script will collect request data and provide a recommended configuration:

```bash
journalctl -fu iota-node | setups/validator/config-traffic-control.sh "YOUR_KNOWN_IP_ADDRESS"
x-forwarded-for contents: YOUR_KNOWN_IP_ADDRESS
Configuration:
  client-id-source:
    x-forwarded-for: 1
```

5. Set the configuration as specified by the script.
6. Restart your node to apply the new configuration.

The script automatically calculates the correct number of hops by analyzing the position of your known IP address in the `x-forwarded-for` header.

## Recommended Production Settings

For production validator nodes, we recommend:

```yaml
policy-config:
  # Use socket-addr for direct connections or x-forwarded-for for proxied setups
  client-id-source: socket-addr  # Adjust based on your setup
  
  connection-blocklist-ttl-sec: 300  # Block for 5 minutes
  proxy-blocklist-ttl-sec: 300  # Block for 5 minutes
  
  spam-policy-type:
    freq-threshold:
      # Adjust these thresholds based on your expected legitimate traffic
      client-threshold: 50  # Sustained tallies per second
      proxied-client-threshold: 10  # Sustained tallies per second per client behind proxy
      burst-secs: 30
  
  # Consider enabling error policy for production
  error-policy-type:
    freq-threshold:
      client-threshold: 20  # Error tallies per second
      proxied-client-threshold: 5
      burst-secs: 30
  
  spam-sample-rate: 0.5  # Sample half of all requests
  dry-run: false  # Ensure this is false for actual protection
```

## Change Traffic Control at Runtime

The admin API of the node (`admin-interface-address`, `127.0.0.1:1337` by default) reads and changes traffic control while the node runs. Every change lasts until the node restarts. To keep a change, write it to the node configuration.

| Request | Does |
| --- | --- |
| `GET /traffic-control` | Shows the settings in force, as JSON |
| `GET /traffic-control/config` | Shows the settings in force in the shape of `policy-config`, as JSON |
| `POST /traffic-control?...` | Changes `error_threshold`, `spam_threshold`, `dry_run`, `connection_blocklist_ttl_sec`, `proxy_blocklist_ttl_sec`, `default_action`, `simulation_gas_per_sec` and `simulation_burst_gas` |
| `GET /traffic-control/rules` | Shows the access rules |
| `POST /traffic-control/rules/add?list=allow&client=198.51.100.0/24` | Adds an `allow` or `deny` rule |
| `POST /traffic-control/rules/remove?list=allow&client=198.51.100.0/24` | Removes a rule |
| `GET /traffic-control/blocklist?limit=200` | Shows the blocked clients, with the reason (`spam`, `error` or `manual`) and the seconds left |
| `POST /traffic-control/block?client=203.0.113.9&ttl_sec=3600` | Blocks a client, with the reason `manual` |
| `POST /traffic-control/unblock?client=203.0.113.9` | Removes the block of a client, and resets its policy counts and gas balance, also when it had no block |
| `GET /traffic-control/clients?top=20` | Shows the clients with the lowest simulation gas balances, and the blocked clients |

`iota-tool admin traffic-control` calls these routes. Its commands are `status`, `set`, `rules list`, `rules allow|deny add|remove <client>`, `blocklist`, `block <client> --ttl <seconds>`, `unblock <client>` and `clients`:

- Listings print tables. With `--json`, the commands print JSON.
- The changes print the answer of the node. `set` writes that answer to standard error, then prints the settings in force.
- `set --default-action deny` shows the warning below and asks to confirm the change first. `--yes` skips the question.
- The commands reach `http://127.0.0.1:1337` unless `--admin-url` names another address.

`iota-tool admin traffic-control save --config <node config file>` writes the settings in force to the `policy-config` of the file:

- It shows the change and asks to confirm it. `--yes` skips the question.
- It keeps the old file next to it, with the suffix `.<unix seconds>.bak`.
- The new file gets the mode of the old one. When `save` runs as root, the new file also gets the owner of the old one.
- It writes the whole file again, so the comments of the file are lost.
- Blocks are not part of the configuration, so `save` does not keep them.
- It writes the file in place, so the file and its folder must be writable. Where the config is mounted read-only or as a single file, as in the Docker setup, add `--output <file>`. `save` then writes the new config to that file. Copy it over the config on the host, for example with `docker cp`.

`blocklist` shows at most `limit` blocks, and `clients` at most `top` gas balances and `top` blocks, 200 by default. A listing says how many entries it left out. The spam and error policies cannot report what they counted for a client, so `clients` shows only the gas balances and the blocks.

When the node blocks a client after a breach of the spam or error policy, or by a manual block, it logs the line `client_blocked client=<client> reason=<spam|error|manual> ttl_secs=<seconds>` at level `info` under the log target `iota_node::client_blocked`, outside dry run. Host firewall tools such as fail2ban and CrowdSec can act on this line. Deny rules, the default action `deny`, and blocks of clients that reach the node through a fullnode refuse requests without this line.

`block` and `unblock` take an IP address, or an IPv6 prefix as the blocklist names it, such as `2001:db8:1:2::/64`:

- A manual block of an IPv6 address blocks its whole `ipv6-prefix-len` prefix.
- A manual block refuses the requests whose client is the blocked address or prefix: the address that connects to the node, the one that `client-id-source` names, or a user that a trusted forwarder names. A manual block of a forwarder also refuses the requests in which it names a user. Like the access rules, it does not refuse requests that reach the node through a fullnode.
- A manual block never shortens a block in force. When it outlasts a block whose line the node logged, the node logs the block line again.
- The node rejects a manual block of a client that an allow rule serves, since a firewall that acts on the block line would ban that client.
- Under dry run the node keeps the block, but still serves the client.
- An unblock also removes the block of the client where it reached the node through a fullnode. It resets what the spam and error policies counted for the client, and its gas balance, also when the client had no block; otherwise the next request of the client would block it again.
- For a block whose block line it logged, the node logs a `client_unblocked client=<client>` line under the same log target, `iota_node::client_blocked`, so a firewall that acts on the block line can lift its ban.

Outside dry run, `default_action=deny` refuses every client that no allow rule names. On a validator this also refuses the other nodes that send it requests. With `client-id-source: socket-addr`, add allow rules for them first. With `x-forwarded-for`, allow rules cannot admit them, as [Proxy Mode Configuration](#proxy-mode-configuration) explains.

A rejected request answers `400 Bad Request` with the reason. The node also rejects a request with a query parameter that the route does not take, and the answer names that parameter.

## Monitoring and Tuning

After enabling the `TrafficController`, monitor your node's metrics to ensure legitimate traffic isn't being blocked. Key metrics to watch:

- `tallies`
- `connection_ip_blocklist_len`
- `proxy_ip_blocklist_len`
- `requests_blocked_at_protocol`
- `traffic_control_num_dry_run_blocked_requests`
- `traffic_control_num_dry_run_deny_rule_requests`
- `traffic_control_num_dry_run_default_deny_requests`
- `traffic_control_allow_rule_requests`
- `traffic_control_deny_rule_requests`
- `traffic_control_allow_rules`, `traffic_control_deny_rules` and `traffic_control_default_deny`
- `traffic_control_simulation_gas_charged`, `traffic_control_simulation_gas_refusals` and `traffic_control_num_dry_run_simulation_gas_refusals`
- `traffic_control_simulation_gas_per_sec` and `traffic_control_simulation_burst_gas`
- `traffic_control_unresolved_client_requests`
- `traffic_control_forwarded_requests`
- `connection_blocklist_ttl_sec`
- `proxy_blocklist_ttl_sec`

Start with `dry-run: true` to observe what would be blocked without actually blocking traffic, then adjust thresholds as needed before setting `dry-run: false`.

## Troubleshooting

If legitimate traffic is being blocked:

1. Increase the `client-threshold` and `proxied-client-threshold` values.
2. Decrease the `connection-blocklist-ttl-sec` and `proxy-blocklist-ttl-sec` values.
3. Increase `burst-secs` to permit larger bursts.

If you're still experiencing DoS attacks:

1. Decrease the thresholds.
2. Increase the blocklist TTL values.
