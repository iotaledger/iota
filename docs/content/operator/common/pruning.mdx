
Sustainable disk usage requires IOTA full nodes to prune the information about historic object versions as well as historic transactions with the corresponding effects and events, including old checkpoint data.

All three kinds of pruning below run at the epoch boundary, where an expired epoch's data is dropped as a whole set of RocksDB column families. Most of the disk space comes back with those files. What is left is a small amount of row-by-row deletion in the live object table, which RocksDB reclaims through background compaction, so the last part of the effect on disk usage is not immediate — see `periodic-compaction-threshold-days` below.

:::tip

Testing indicates that aggressive pruning results in more efficient full node operation.

:::

## Types of Pruning

### Object Pruning

IOTA adds new object versions to the database as part of transaction execution, which makes previous versions ready for garbage collection. Without pruning, this would result in database performance degradation and require large amounts of storage space. A superseded version is moved into its epoch's store as it is superseded, and the whole epoch is dropped once it falls outside the retention window.

### Transaction Pruning

Transaction pruning removes previous transactions, their effects and events, and the corresponding checkpoint data from the database. Each is written into the store of the epoch that executed it, and the whole epoch is dropped once it falls outside the retention window.

### Index Pruning

Index pruning drops the expired epochs of the `rpc_indexes` store, the single secondary index store both the JSON-RPC and the gRPC API read from, so older entries are no longer served by index-backed queries (for example `iotax_getBalance()`, dynamic-field lookups, event queries, and owned-object listings). Without it, the index adds a set of tables per epoch and grows without bound. Index pruning is relevant for every node that maintains the store, which is any node serving the JSON-RPC API (`enable-jsonrpc-api: true`, the default) or the gRPC API (`enable-grpc-api: true`).

The index window may be shorter than the checkpoint window, and the only thing that costs is query reach: `iotax_queryTransactionBlocks()` and other query-style endpoints stop returning entries older than the index window, while every transaction the checkpoint window still retains remains fetchable by digest on both APIs and still reports the checkpoint that confirmed it — that answer is read from the ledger, not from the index.

## Pruning Parameters

Object pruning, transaction pruning, and index pruning are independent of one another, and each is gated by its own parameter, so you can enable or disable them individually:

| Pruning task          | Controlling parameter                  | Enabled when                      |
| --------------------- | -------------------------------------- | --------------------------------- |
| Object pruning        | `num-epochs-to-retain`                 | value is not `u64::MAX`           |
| Transaction pruning   | `num-epochs-to-retain-for-checkpoints` | set                               |
| Index pruning         | `num-epochs-to-retain-for-indexes`     | set                               |

All pruning parameters are configured in `fullnode.yaml`. The following annotated block shows every parameter with its default value — copy it into your config and adjust as needed:

```yaml
# Enable the JSON-RPC API, including the index it relies on for queries
# like ownership, balances, and events. Default: true.
# Set to false for validators or nodes that do not serve JSON-RPC requests.
# The gRPC API maintains the same index under its own flag (enable-grpc-api,
# default: false), so a node with either of the two prunes its indexes.
enable-jsonrpc-api: true

authority-store-pruning-config:
  # Number of epochs to keep historic object versions. Controls object pruning.
  #   0        — aggressive pruning (default). Prunes old versions as soon as
  #              possible. Lowest disk usage. Recommended for validators and full
  #              nodes that do not serve historic object queries.
  #   N (>= 1) — retains object versions from the last N epochs. Use this when
  #              the node must serve lookups by object ID + version.
  #   u64::MAX — disables object pruning entirely (18446744073709551615).
  # Independent of num-epochs-to-retain-for-checkpoints below: historic object
  # versions are retained per epoch and dropped a whole epoch at a time, so
  # object pruning never reads a checkpoint's contents.
  num-epochs-to-retain: 0

  # Number of epochs to keep historic transactions, effects, events, and
  # checkpoint data. Controls transaction pruning.
  #   unset — transaction pruning disabled (default keeps everything).
  #   N     — keeps the N most recent epochs, counting the current one as
  #           one of them. 0 and 1 both keep the current epoch only.
  # num-epochs-to-retain-for-checkpoints: 2

  # Number of historic epochs to retain in the rpc_indexes store, on top of
  # the current one. The store serves both the JSON-RPC and the gRPC API.
  # Controls index pruning. Relevant whenever the node maintains that store
  # (enable-jsonrpc-api: true or enable-grpc-api: true).
  #   unset    — index pruning disabled (default).
  #   0        — keeps the current epoch only, prunes everything older.
  #   N (>= 1) — also keeps the N epochs before the current one.
  # The epoch currently being executed is always retained, whatever this is
  # set to: a client that submits a transaction needs to read it back — the
  # transaction, its effects, and the index rows behind queries — seconds
  # later. Only at an epoch boundary is dropping that data acceptable.
  # May be shorter than num-epochs-to-retain-for-checkpoints above — the
  # only cost is query reach, since every retained transaction stays
  # fetchable by digest and still reports its checkpoint regardless of
  # index retention. It must not exceed that value while transaction
  # pruning is enabled: the node refuses to start otherwise, since
  # iotax_queryTransactionBlocks() would then return transactions the
  # ledger has already pruned. Leaving this unset skips that check, but
  # then the index keeps growing with no bound of its own.
  # num-epochs-to-retain-for-indexes: 2

  # Number of recent per-epoch RocksDB databases to keep. Default: 3.
  num-latest-epoch-dbs-to-retain: 3

  # Trigger periodic compaction for SST files older than this many days.
  # Reclaims disk space and avoids fragmentation. Default: 1 (when read from
  # config). Set to "null" to disable periodic compaction entirely.
  periodic-compaction-threshold-days: 1
```

All three run at the epoch boundary, where the node drops the epochs that have
fallen outside each retention window. Each retention value counts the epoch the
node is entering as one of the epochs it keeps.

## Configuration Examples

The following examples cover common operator use cases. Each example shows the key parameters for the scenario — parameters not listed use their defaults from the [reference block above](#pruning-parameters).

### Validator or Minimal Full Node

This configuration keeps disk usage to a minimum. A node with this setup cannot answer queries that require indexing or historic data. It is the recommended setup for IOTA validators and for full nodes that do not serve RPC requests.

```yaml
# Do not serve the JSON-RPC API, or maintain the index it depends on
enable-jsonrpc-api: false

authority-store-pruning-config:
  # Aggressively prune historic object versions
  num-epochs-to-retain: 0
  # Prune historic transactions of past epochs
  num-epochs-to-retain-for-checkpoints: 2
```

### Full Node with Indexing but no History

This setup manages secondary indexing in addition to the latest state, but aggressively prunes historic data. A full node with this configuration:

- Answers RPC queries that require indexing, like `iotax_getBalance()`.
- Answers RPC queries that require historic transactions via a fallback to retrieve the data from a remote key-value store: `iota_getTransactionBlock()`.
- Cannot answer RPC queries that require historic object versions: `iota_tryGetPastObject()`.
  - The `showBalanceChanges` filter of `iota_getTransactionBlock()` relies on historic object versions, so it cannot work with this configuration.

```yaml
authority-store-pruning-config:
  # Aggressively prune historic object versions
  num-epochs-to-retain: 0
  # Prune historic transactions of past epochs
  num-epochs-to-retain-for-checkpoints: 2
```

### Full Node with Full Object History but Pruned Transaction History

This configuration manages the full object history while still pruning historic transactions. A full node with this configuration can answer all historic and indexing queries (using the transaction query fallback for transactional data), including the ones that require historic objects such as the `showBalanceChanges` filter of `iota_getTransactionBlock()`.

The main caveat is disk usage: the full object history grows without bound. You should closely monitor the disk space growth on a full node with this configuration.

```yaml
authority-store-pruning-config:
  # No pruning of object versions (use u64::max for num of epochs)
  num-epochs-to-retain: 18446744073709551615
  # Prune historic transactions of the past epochs
  num-epochs-to-retain-for-checkpoints: 2
```
