## About Time-Locked Accounts

Time-locked accounts combine public key authentication with time-based access control. An account remains locked until a specified unlock time (Unix timestamp in milliseconds) is reached. This enables delayed access scenarios like vesting schedules, future payments, or timed releases.

The unlock time is stored as a dynamic field, and authenticators verify both the signature and whether the current time has passed the unlock threshold.

## What this example shows

- Create a time-locked IOTAccount with a public key and unlock time.
- Authenticate using both signature verification and time checks.
- Support two time sources: Clock object or epoch timestamp.
- Manage (attach, rotate, remove) unlock times on accounts.

## How it works

### Step 1: Create time-locked account

Create an IOTAccount that requires both a valid signature and a time check before allowing transactions.
```move file=<rootDir>/examples/move/abstract_iota_accounts/time_locked/sources/time_locked_iotaccount.move#L36-L63
```

**What this does**
- Creates a new IOTAccount with both public key and unlock time protection.
- The `unlock_time` is a Unix timestamp in milliseconds (e.g., `1234567890000`).
- Optionally sets an admin address for account management.
- The account cannot be used until the current time reaches or exceeds the unlock time.

### Step 2: Attach unlock time to account builder

Helper function to add unlock time when building an account through the builder pattern.
```move file=<rootDir>/examples/move/abstract_iota_accounts/time_locked/sources/time_locked_iotaccount.move#L65-L68
```

**What this does**
- Adds unlock time as a dynamic field during account construction.
- Enables flexible account setup with multiple configuration options.

### Step 3: Manage unlock time (rotate, add, remove)

Functions to update or remove time-based restrictions after account creation.
```move file=<rootDir>/examples/move/abstract_iota_accounts/time_locked/sources/time_locked_iotaccount.move#L73-L91
```

**What this does**
- `rotate_unlock_time`: Updates the unlock time and optionally the public key and authenticator.
- `add_unlock_time`: Adds time-lock protection to an existing account.
- `remove_unlock_time`: Removes time-based restrictions entirely.

### Step 4: Authenticate with Clock object

Verifies both the signature and that the Clock's current time has passed the unlock time.
```move file=<rootDir>/examples/move/abstract_iota_accounts/time_locked/sources/time_locked_iotaccount.move#L111-L124
```

**What this does**
- First verifies the Ed25519 signature against the stored public key.
- Then checks if the Clock object's timestamp is greater than or equal to the unlock time.
- Transactions fail if either check fails.



### Step 5: Authenticate with epoch timestamp

Alternative authentication using the transaction context's epoch timestamp instead of Clock.
```move file=<rootDir>/examples/move/abstract_iota_accounts/time_locked/sources/time_locked_iotaccount.move#L130-L142
```

**What this does**
- Verifies the Ed25519 signature.
- Uses epoch timestamp from transaction context (no Clock object needed).
- Suitable when Clock object access is not available or desired.


### Step 6: Core unlock time verification

The underlying authentication logic that enforces the time lock.
```move file=<rootDir>/examples/move/abstract_iota_accounts/time_locked/sources/unlock_time_authentication.move#L71-L79
```

**What this does**
- Retrieves the stored unlock time from the account's dynamic fields.
- Compares current time against unlock time.
- Rejects transactions if `current_time < unlock_time`.

### Step 7: Attach and manage unlock time (low-level)

Core functions for managing unlock time data as dynamic fields.
```move file=<rootDir>/examples/move/abstract_iota_accounts/time_locked/sources/unlock_time_authentication.move#L33-L53
```


**What this does**
- `attach_unlock_time`: Adds unlock time to an account's UID.
- `detach_unlock_time`: Removes unlock time and returns the value.
- `rotate_unlock_time`: Updates the unlock time to a new value.
- These are the underlying primitives used by higher-level account functions.

### Step 8: View and query unlock time
```move file=<rootDir>/examples/move/abstract_iota_accounts/time_locked/sources/time_locked_iotaccount.move#L147-L154
```

**What this does**
- `has_unlock_time`: Checks if an account has a time lock configured.
- `borrow_unlock_time`: Returns a reference to the unlock timestamp.
- Useful for querying account status before attempting transactions.

## Verify the result:

**Create time-locked account**
```bash
# Set unlock time (Unix timestamp in milliseconds)
export UNLOCK_TIME=1234
export PTB_JSON=$(iota client ptb \
--move-call 0x2::authenticator_function::create_auth_function_ref_v1 '<'$PACKAGE_ID'::'$ACCOUNT_MODULE_NAME'::'$ACCOUNT_TYPE_NAME'>' @$METADATA_ID '"'$AUTH_MODULE_NAME'"' '"'$AUTH_FUNCTION_NAME'"' \
--assign ref \
--move-call $PACKAGE_ID::$CREATE_MODULE_NAME::$CREATE_FUNCTION_NAME vector"$SIGN_PUB_KEY_BYTES" none $UNLOCK_TIME ref \
--json)
export ABSTRACTACCOUNT=$(echo $PTB_JSON | jq -r '.objectChanges[] | select(.type == "created" and (.objectType | endswith("::'$ACCOUNT_MODULE_NAME'::'$ACCOUNT_TYPE_NAME'"))) | .objectId')
echo "Account Object ID: $ABSTRACTACCOUNT"
```

## Expected Behavior
- Transactions fail with `EAccountStillLocked` error if executed before the unlock time.
- Once the unlock time is reached, transactions succeed with valid signatures.
- Two authenticator options: Clock-based (requires Clock object) or epoch-based (uses transaction context).
- The unlock time can be rotated to extend or shorten the lock period.
