## About Lean IMT Accounts

Lean IMT (Incremental Merkle Tree) Accounts enable shared account control by a large group of addresses using zero-knowledge proofs. Public keys are hashed with Poseidon and inserted into a Lean IMT. Any address in the tree can authenticate without revealing their identity (secret mode) or by disclosing their public key (public key mode).

This is ideal for airdrops, DAOs, or any scenario where many addresses need to act through a single account without individual on-chain transactions for each member.

:::note
This is a proof-of-concept. A production implementation would require salt mechanisms and additional security measures to prevent unauthorized access if a public key is disclosed.
:::

## What this example shows

- Create a LeanIMTAccount with a Merkle tree root representing authorized addresses.
- Authenticate using Groth16 zero-knowledge proofs of Merkle tree membership.
- Support two modes: secret (anonymous) and public key (disclosed identity).
- Hash addresses using Poseidon for efficient zero-knowledge verification.
- Verify membership proofs on-chain without revealing the prover's identity.

## How it works

### Step 1: Define LeanIMTAccount structure

The account struct holds the UID and the Merkle tree root.
```move file=<rootDir>/examples/move/abstract_iota_accounts/lean_imt_account/sources/lean_imt_account.move#L20-L30
```

**What this does**
- Stores the account's unique identifier (UID).
- Holds the root hash of the Lean Incremental Merkle Tree.
- The root represents all addresses authorized to use this account.
- Dynamic fields can be added for additional functionality.

### Step 2: Create Lean IMT account with tree root

Create an account that stores the root of a Merkle tree containing authorized addresses.
```move file=<rootDir>/examples/move/abstract_iota_accounts/lean_imt_account/sources/lean_imt_account.move#L34-L45
```

**What this does**
- Creates a new LeanIMTAccount as a shared object.
- Stores the Merkle tree root representing all authorized addresses.
- Sets up the authenticator for zero-knowledge proof verification.
- The root is generated off-chain from a set of hashed addresses.

### Step 3: Rotate account root (admin only)

Update the Merkle tree root to change the set of authorized addresses.
```move file=<rootDir>/examples/move/abstract_iota_accounts/lean_imt_account/sources/lean_imt_account.move#L51-L57
```

**What this does**
- Allows updating the root to add/remove authorized addresses.
- Only the account itself can call this function (sender must be account).
- **Warning**: This is unsafe without proper access control; consider using an admin capability.
- Rotating the root effectively changes which addresses can authenticate.

### Step 4: Secret mode authenticator (anonymous)

Authenticate without revealing the public key by using a separate signing key.
```move file=<rootDir>/examples/move/abstract_iota_accounts/lean_imt_account/sources/lean_imt_account.move#L64-L82
```

**What this does**
- Uses a `signing_public_key` different from the main public key for transaction signing.
- Accepts a `leaf` (hash of the actual public key) without revealing it.
- Verifies the signature against the signing key.
- Proves the leaf is in the Merkle tree using a zero-knowledge proof.
- Maintains privacy by not disclosing the main public key on-chain.


### Step 5: Public key mode authenticator (disclosed identity)

Authenticate with the public key disclosed on-chain.
```move file=<rootDir>/examples/move/abstract_iota_accounts/lean_imt_account/sources/lean_imt_account.move#L88-L104
```

**What this does**
- Uses the same key for both signing and tree membership.
- Derives the leaf directly from the public key.
- Verifies the signature and proof in one step.
- Simpler than secret mode but reveals the user's identity.

### Step 6: Secret mode authentication logic

Core authentication implementation for secret mode with separate signing key.
```move file=<rootDir>/examples/move/abstract_iota_accounts/lean_imt_account/sources/lean_imt_account.move#L112-L124
```

**What this does**
- Verifies the Ed25519 signature using the signing public key.
- Validates the zero-knowledge proof that the leaf is in the tree.
- Ensures the transaction digest matches the signature.
- Prevents replay attacks through signature verification.

### Step 7: Public key mode authentication logic

Authentication implementation when disclosing the public key.
```move file=<rootDir>/examples/move/abstract_iota_accounts/lean_imt_account/sources/lean_imt_account.move#L129-L141
```

**What this does**
- Verifies the signature using the disclosed public key.
- Derives the leaf from the public key (double Poseidon hash).
- Validates the proof that this derived leaf is in the tree.
- Simpler flow since signing key and tree membership key are the same.

### Step 8: Verify Groth16 zero-knowledge proof

Core proof verification using the Groth16 proving system.
```move file=<rootDir>/examples/move/abstract_iota_accounts/lean_imt_account/sources/lean_imt.move#L12-L26
```

**What this does**
- Prepares the verifying key for the BN254 elliptic curve.
- Combines the root and leaf as public inputs to the proof.
- Converts proof points and public inputs from bytes.
- Verifies the Groth16 proof on-chain using the BN254 curve.
- Aborts if the proof is invalid (member not in tree).

### Step 9: Hash address using Poseidon

Hash an address for inclusion in the Merkle tree using Poseidon hash.
```move file=<rootDir>/examples/move/abstract_iota_accounts/lean_imt_account/sources/lean_imt.move#L32-L54
```

**What this does**
- Converts address/bytes to two vectors of u256 values.
- Splits the 32-byte input into two 16-byte chunks.
- Applies Poseidon hash (BN254) to each chunk separately.
- Combines the two hashes with a final Poseidon hash.
- Produces a hash suitable for zero-knowledge circuits.

### Step 10: Derive leaf from public key

Generate the Merkle tree leaf from a public key.
```move file=<rootDir>/examples/move/abstract_iota_accounts/lean_imt_account/sources/lean_imt.move#L56-L60
```

**What this does**
- Hashes the public key with Blake2b256 to derive an address.
- Hashes the address bytes with Poseidon (first hash).
- Hashes the result again with Poseidon (double hash).
- Returns the final leaf value for Merkle tree insertion.
- This double-hashing provides the structure needed for ZK proofs.

## Verify the result

**Generate tree and proofs**
```bash
# Clone the repository for proof generation
git clone https://github.com/miker83z/iota-lean-imt-account
cd iota-lean-imt-account

# Generate the tree root from a set of addresses
# This creates the Merkle tree and outputs the root
ADDRESS=0x6b72f63997aa75e2aff.... cargo run --bin hash_address

# Generate a membership proof for a specific address
ADDRESS=0x6b72f63997aa75e2aff8e7c..... cargo run --bin generate_claim_proof
```

**Create Lean IMT account**
```bash
# Set the Merkle tree root
export ROOT_HEX="4b61023a56e6b37edec2ba55c1b3f0cf0f4789431aafd6da10d32de09bb97402"
export ROOT_BYTES=$(python3 -c "import sys; print([int('$ROOT_HEX'[i:i+2],16) for i in range(0,len('$ROOT_HEX'),2)])")
export PTB_JSON=$(iota client ptb \
--move-call 0x2::authenticator_function::create_auth_function_ref_v1 '<'$PACKAGE_ID'::'$ACCOUNT_MODULE_NAME'::'$ACCOUNT_TYPE_NAME'>' @$METADATA_ID '"'$AUTH_MODULE_NAME'"' '"'$AUTH_FUNCTION_NAME'"' \
--assign ref \
--move-call $PACKAGE_ID::$CREATE_MODULE_NAME::$CREATE_FUNCTION_NAME vector"$ROOT_BYTES" ref \
--json)
export ABSTRACTACCOUNT=$(echo $PTB_JSON | jq -r '.objectChanges[] | select(.type == "created" and (.objectType | endswith("::'$ACCOUNT_MODULE_NAME'::'$ACCOUNT_TYPE_NAME'"))) | .objectId')
echo "Account Object ID: $ABSTRACTACCOUNT"
```

## Expected Behavior
- Transactions with invalid zero-knowledge proofs are rejected.
- Secret mode allows authentication without revealing the public key on-chain.
- Public key mode simplifies the process by using one key for both signing and membership.
- The account can be shared by many addresses without individual on-chain registrations.
- Rotating the root changes which addresses are authorized to use the account.
