# Verify a Proof Using a Trusted Node

Trusted-node committee resolution accepts the committee reported by the connected node without authenticating its lineage from genesis. Use this mode only when the selected gRPC endpoint is already inside the verifier's trust boundary.

:::warning
Trusted-node mode does not authenticate committee lineage. A malicious or compromised trusted node can choose the committee that the verifier accepts.
:::

## Prerequisites

- Complete the [Rust](../../../getting-started/rust.mdx) or [Wasm](../../../getting-started/wasm.mdx) setup.
- Select an active IOTA CLI environment and wallet with funds or faucet access.
- Make sure the JSON-RPC and gRPC endpoints belong to the same network.
- Use a gRPC endpoint operated by a party you trust.

:::important

The example creates a new Locked Notarization transaction. On mainnet, fund the active wallet and set `IOTA_NOTARIZATION_PKG_ID` to an existing Single Notarization Move Package before running it.

:::

### 2. Verify Using the Node's Committee

Select trusted-node committee resolution and verify the proof against the committee supplied by the connected node. Successful verification authenticates the proof relative to that node, so the node remains part of the trust boundary.

## Expected Behavior

- The proof contains the transaction created by the example.
- Verification succeeds without loading a genesis blob or walking committee history.
- The verified result exposes the authenticated transaction digest and checkpoint sequence number.
- The connected node remains responsible for supplying the committee that the verifier accepts.
