# Build a Committee Cache

Persist authenticated committees between runs with a file-backed Rust cache. Read [Committee Caching](../../explanations/trust-and-verification.mdx#committee-caching) for cache behavior and strategy choices.

## Prerequisites

- Complete the [Rust example setup](https://github.com/iotaledger/notarization/tree/v0.1/examples/poi/README.md#prerequisites), including network, wallet, and package configuration.
- Obtain an independently trusted genesis blob for the selected network.
- Choose a writable cache directory protected from untrusted modification.

This example is Rust-only; the Wasm Package does not expose a custom committee-cache interface. See the [cache reference](#committee-cache-reference) for constructor options and the storage contract.

## Build the File-Backed Cache

The example stores one BCS file per network and epoch. The same design can be adapted to a database table with a composite `(chain_identifier, epoch)` key or a key-value store with both values encoded in its key.

## Run the Example

Run the file-backed implementation from the Notarization repository root:

```bash
cargo run --release -p examples --example advanced_01_committee_cache
```

Run it again against the same network to reuse the committees stored during the first verification. The example prints the cache directory and verification duration so you can confirm which storage it uses.

## Committee Cache Reference

### Choose an Anchored Constructor

The cache works with both anchored constructor variants:

| Constructor | Trust input | Network scoping |
| --- | --- | --- |
| `from_genesis_with_cache(genesis, cache)` | A trusted BCS-encoded `genesis.blob` | Derives the chain identifier and epoch 0 committee from the genesis checkpoint. |
| `anchored_with_cache(chain_identifier, committee, cache)` | An already trusted committee | Requires the trusted genesis checkpoint digest explicitly, even when the anchor belongs to a later epoch. |

Prefer `from_genesis_with_cache()` when your application already has the network's trusted genesis blob. Use `anchored_with_cache()` when another trusted process supplies both the anchor committee and the correct chain identifier.

### Implement the Cache Contract

The `CommitteeCache` trait has one lookup operation and one store operation. Both receive a `CommitteeCacheKey`, which exposes the chain identifier and epoch.

<div className={'hide-code-block-extras'}>

```rust reference
https://github.com/iotaledger/notarization/tree/v0.1/poi-rs/src/cache.rs#L13-L81
```

</div>

A production implementation should follow these rules:

- Return `Ok(None)` only when no value exists for the complete network-and-epoch key.
- Return `CommitteeCacheError::Backend` when storage, decoding, or connectivity fails. Do not treat a backend failure as a cache miss.
- Check that the stored committee's epoch matches the key's epoch.
- Make repeated writes of the same committee succeed without changing the entry.
- Return `CommitteeCacheError::Conflict` if another committee already occupies that key.
- Prevent partial writes and races with atomic file operations, a database transaction, or a conditional key-value-store write.
- Restrict write access to the verifier process and apply the durability and backup controls required for other trust-sensitive application state.

BCS is a convenient storage format because the file example already uses it, but the trait does not require a particular serialization format or backend.
