# Building a Full-Stack IOTA Identity University Degree Verification System Guided Code Workshop

In this workshop, we will build a production-ready **University Degree Verification system** using **IOTA Identity**, **Rust**, and **React.** By the end of this workshop, you’ll have a complete, end-to-end flow demonstrating how **Issuers**, **Holders**, and **Verifiers** interact in a real-world university degree validation scenario — all powered by IOTA Identity. We will build the application piece-by-piece, focusing on the communication flow for each of the four core identity steps (DID creation, VC issuance, VP creation, and Verification).

## Prerequisites

Before starting this workshop, make sure you have:

- **Rust** (latest stable version) installed → Install Rust
- **Cargo** (comes with Rust) for building and running projects
- A **local IOTA network** running with the IOTA Identity contract deployed
    - See [Local Network Setup](https://docs.iota.org/developer/iota-identity/getting-started/local-network-setup)
    - Ensure you can request test tokens from the faucet
- A code editor such as **VS Code**
- (Optional but recommended) Basic familiarity with:
    - **IOTA Decentralized Identifiers (DIDs)**
    - **IOTA Verifiable Credentials (VCs)** and **IOTA Verifiable Presentations (VPs)**

## The Problem

Today, verifying university degrees is a slow, manual, and often costly hurdle. Employers must contact universities or rely on centralized third-party services, which is costly and prone to fraud. Fake certificates can easily circulate.

## The Opportunity

Universities can issue tamper-proof Verifiable Credentials (VCs) that students control using the IOTA Identity product. Students present these credentials to employers, who can instantly verify them on the IOTA network without intermediaries, cutting costs and eliminating fraud.

### What You’ll Build in this Workshop

We're building a complete, production-ready system that connects a modern React frontend to a high-performance Rust backend. You'll learn how the frontend triggers the entire IOTA Identity lifecycle:

- **Holder (Student)**: Creates a DID and stores it securely.
- **Issuer (University)**: Issues a **Verifiable Credential (VC)** representing the degree.
- **Holder**: Packages the credential into a **Verifiable Presentation (VP)** and signs it.
- **Verifier (Employer)**: Verifies the authenticity of the presentation and credentials against the IOTA network.

## Part 2: Building the Front-to-Back Connection

This section demonstrates how every button on the frontend connects to a specific function on the Rust backend, completing the identity flow.

### Step 2.1: The Communication Layer (`handleApiCall`)

In your **React Frontend** (`src/App.jsx`), this function is the central bridge. It standardizes how all API requests are made, ensuring the required `packageId` and error handling are used for every step.

```JavaScript
// src/App.jsx (Excerpt: handleApiCall)

const handleApiCall = useCallback(async (step, endpoint, body) => {
    // ... validation and state updates omitted for brevity ...

    // Sends POST request to Rust API.
    // NOTE: { packageId, ...body } sends the required packageId plus step-specific data.
    const response = await fetch(`${apiUrl}${endpoint}`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ packageId, ...body }), 
    });

    if (!response.ok) {
        // Essential: Catches Rust's HTTP errors (like 404 or 500) and displays them.
        const errorText = await response.text();
        throw new Error(`API returned status ${response.status}: ${errorText}`);
    }

    const data = await response.json();
    setLoadingStep(0);
    return data; // Returns the result (DID, JWT, or Validation log)
}, [packageId, apiUrl]);
```

## Explanation:

- What it does: This function sends HTTP POST requests to the Rust backend’s API endpoints (e.g., `/holder/create-did`). It includes a `packageId` (required for IOTA Identity) and handles errors by checking the response status. The result (e.g., a DID or JWT) is returned to update the frontend state.
- Why it matters: Centralizes API communication, ensuring consistent error handling and payload formatting across all steps. The `useCallback` hook optimizes performance by memoizing the function.
- Key concepts:
    - HTTP POST: Sends data (e.g., `packageId, vcJwt`) to the backend.
    - Error Handling: Catches HTTP errors (e.g., 404, 500) and displays meaningful messages.
    - State Updates: Stores results (e.g., DID, JWT) in React state for display.

### Step 2.2: Step 1: Holder Creates DID

**Frontend** (`src/App.jsx`): We define the handler to call the API endpoint and update the state.

```JavaScript

const handleCreateDid = async () => {
    // Calls the Rust endpoint. Body is empty as the DID logic is self-contained.

// This handler is attached to the "Execute Step 1" button.
```

## Explanation:

- What it does: The handleCreateDid function triggers a POST request to the backend’s /holder/create-did endpoint. It sends an empty body since the backend handles all DID creation logic. The returned DID string is stored in the React state (setDid) for display in the UI.
- Why it matters: This initiates the IOTA Identity flow by creating a unique identifier for the student (Holder), which is used in later steps (e.g., VC issuance). It connects the frontend button to the backend logic.
- Key concepts:
 - DID: A decentralized identifier (e.g., did:iota:...) that uniquely identifies the student.
 - React State: Stores the DID for display and use in subsequent steps.
 - API Call: Uses handleApiCall to communicate with the backend.

**Backend** (`src/main.rs`): The Rust function uses the received `package_id` to initialize the client and runs the core creation logic.

```Rust
// iota-identity-backend/src/main.rs (holder_create_did)

    // Rust logic calls create_or_load_did, which handles funding and anchoring the DID
    let (holder_doc, _) = create_or_load_did(
        "./holder_doc.json", /* ... */
    ).await.map_err(/* ... error handling ... */)?;

    // Responds to the frontend with the DID string

    }))

```
## Explanation:

- What it does: The holder_create_did function handles the /holder/create-did endpoint. It calls create_or_load_did (a utility function) to either create a new DID or load an existing one from holder_doc.json. The DID is anchored to the IOTA network, and the function returns a JSON response containing the DID string.
- Why it matters: This creates the student’s identity on the IOTA network, stored securely using Stronghold. The DID is the foundation for issuing and verifying credentials.
- Key concepts:
    - DID Creation: Uses IOTA Identity to generate and publish a DID document.
    - Stronghold: Securely stores the DID’s private keys.
    - Axum Endpoint: Handles HTTP requests and returns JSON responses.

## Explanation:

- What it does: The `handleCreateVp` function sends a POST request to the `/holder/create-vp` endpoint, including the VC JWT (`vcJwt`) from the previous step. The backend returns a VP JWT, which is stored in the React state (`setVpJwt`) for display and verification.
- Why it matters: This allows the student to create a signed VP, proving they own the VC when presenting it to an employer.
- Key concepts:
    - VP: A signed package containing the VC, proving the Holder’s ownership.
    - Payload: Sends the VC JWT to the backend for inclusion in the VP.
    - React State: Stores the VP JWT for the final verification step.

## Explanation:

- What it does: The `holder_create_vp` function handles the `/holder/create-vp` endpoint. It loads the Holder’s DID and Stronghold storage, creates a VP embedding the provided VC JWT (`body.vc_jwt`), signs it with the Holder’s private key, and adds a nonce (challenge) for security. The VP JWT is returned to the frontend.
- Why it matters: The VP proves the student owns the VC and is ready for verification by an employer.
- Key concepts:
    - VP Creation: Embeds the VC in a presentation and signs it.
    - Nonce: A unique challenge (e.g., `challenge-123`) ensures the VP is fresh.
    - Stronghold: Securely accesses the Holder’s private key for signing.

- What it does: The `handleValidateVp` function sends a POST request to the `/verifier/validate` endpoint with the VP JWT (`vpJwt`). The backend returns a validation result (log and success boolean), which updates the React state to display the outcome (e.g., “SUCCESS” or “FAIL”) in the UI.
- Why it matters: This completes the identity flow by verifying the VP’s authenticity, ensuring the degree credential is valid and untampered.
- Key concepts:
    - Validation Result: Displays whether the VP and VC are valid.
    - React State: Updates the UI with the verification log and success status.
    - API Call: Sends the VP JWT to the backend for network-based verification.

**Backend** (`src/main.rs`): This is the final, network-intensive verification step.

```Rust
    // 4. Resolve Issuer's DID (gets public key from network).
    // 5. Validate VC signature against Issuer's public key.
    
    // Returns the full verification log and success boolean to the frontend.

```

## Explanation:

- What it does: The `verifier_validate` function handles the `/verifier/validate` endpoint. It sets up an IOTA resolver to fetch the Holder’s and Issuer’s DID documents from the IOTA network, validates the VP’s signature and nonce, and checks the VC’s signature against the Issuer’s public key. It returns a JSON response with a success boolean and a detailed log.
- Why it matters: This ensures the VP and VC are authentic, untampered, and issued by a trusted university, completing the degree verification process.
- Key concepts:
    - Resolver: Fetches DID documents from the IOTA network to access public keys.
    - Signature Validation: Verifies the VP and VC signatures to ensure authenticity.
    - Nonce Check: Confirms the VP’s freshness using the challenge.

## Troubleshooting

- Network Errors: Ensure the IOTA test network is running and `API_ENDPOINT` is set.
- Dependency Issues: Run `cargo update` or `npm install` to resolve missing dependencies.
- File Not Found: Verify that `holder_doc.json` exists after Step 1.
- HTTP Errors: Check the backend logs for issues like invalid `packageId`.
