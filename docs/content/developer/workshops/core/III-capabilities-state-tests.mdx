# Workshop III Practical — Capabilities, Type-State, Abilities & Tests

In this workshop, you’ll harden ScholarFlow with multi-role capabilities, lifecycle/state-machine guards, and Move unit tests.

## Quick recap

- You published a package and implemented a simple mint flow.
- You created a shared `Registry` and indexed mints with a PTB.

## What’s next

Make real contracts safe by design. Design multi-role access control, encode lifecycle transitions as explicit entry functions, use abilities to prevent footguns, and lock your rules in with unit tests.

### Learning outcomes
- Implement role capabilities (admin/issuer/revoker) and safe rotation.
- Enforce type-state lifecycle: Pending → Active → Revoked, with illegal transitions blocked.
- Audit and fix abilities (key | store | copy | drop) to match intent and conservation.
- Write Move unit tests for authorization, transitions, idempotence, and error codes.

## Prerequisites

- From I & II: a working package with `grant` and (optionally) `registry`.
- IOTA CLI installed.
- Focus here is pure Move + tests.

Export convenience variables (optional on-chain trials):

```bash
export PKG_ID=<0x...package id>
export ADMIN_CAP_ID=<0x...admin cap object id>
export PUBLISHER_ADDR=<0x...publisher address>
```

## Let's plan the hardening

- Replace “single admin does everything” with role caps.
- Make lifecycle explicit: request → approve → revoke (no raw status without guards).
- Tighten abilities on caps and resources (no accidental copy/drop).
- Prove rules with unit tests (positive and expected-failure paths).

## Access control (roles)

Create `sources/access.move`. Define roles, rotation, and checks.


## Lifecycle as type‑state

Create `sources/lifecycle.move`. Encode lifecycle with explicit entries and role gates. Avoid raw “status” unless you strictly guard transitions.

```move
module scholarflow::lifecycle {
    use iota::object::{Self, UID, ID};
    use iota::tx_context::{Self, TxContext};
    use iota::transfer;
    use iota::event;
    use scholarflow::access;

    /// Errors
    const EOnlyIssuer: u64 = 10;
    const EOnlyRevoker: u64 = 11;
    const EInvalidTransition: u64 = 12;

    /// States (string tags to keep events human-readable).
    const S_PENDING: vector<u8> = b"pending";
    const S_ACTIVE: vector<u8>  = b"active";
    const S_REVOKED: vector<u8> = b"revoked";

    /// Lifecycle events
    public struct GrantRequested has copy, drop, store { student: address }
    public struct GrantApproved  has copy, drop, store { grant_id: ID, student: address }
    public struct GrantRevoked   has copy, drop, store { grant_id: ID, by: address }

    /// Resource with explicit lifecycle.
    public struct Grant has key {
        id: UID,
        student: address,
        amount: u64,
        state: vector<u8>, // must be guarded by entries below
    }

    /// Request a grant (creates a pending resource owned by the issuer for review).
    public entry fun request_grant(_student: address, _amount: u64, _roles: &access::Roles, _ctx: &mut TxContext) {
        // Step 1: Read sender from `_ctx`.
        // Step 2: Ensure sender is an issuer via `access::is_issuer`.
        // Step 3: Emit GrantRequested with student.
        // Step 4: Create a Grant with state = S_PENDING.
        // Step 5: Transfer the new Grant to the issuer (sender) for review.
        abort 9001
    }

    /// Approve a pending grant (issuer-only) → ACTIVE and transfer to student.
    public entry fun approve_grant(_g: &mut Grant, _roles: &access::Roles) {
        // Implementer guidance:
        // 1) Ensure only an issuer can approve. Typical check uses tx_context::sender(ctx),
        //    so add a TxContext param in your code if needed, or require an issuer-specific Cap.
        // 2) assert!(_g.state == S_PENDING, EInvalidTransition);
        // 3) Set _g.state = S_ACTIVE;
        // 4) event::emit(GrantApproved { grant_id: object::id(_g), student: _g.student });
        // 5) If policy is "transfer on approve", transfer::transfer(*_g, _g.student) and redesign to pass by value.
        abort 9001
    }

    /// Revoke an active grant (revoker-only) → REVOKED (remain owned or reclaim? define policy).
    public entry fun revoke_grant(_g: &mut Grant, _roles: &access::Roles) {
        // Implementer guidance:
        // 1) Ensure only a revoker can revoke (via tx_context::sender(ctx) or a RevokerCap).
        // 2) assert!(_g.state == S_ACTIVE, EInvalidTransition);
        // 3) Set _g.state = S_REVOKED;
        // 4) event::emit(GrantRevoked { grant_id: object::id(_g), by: /* actor */ 0x0 });
        // 5) Decide policy for ownership on revoke (stay with owner, clawback, or park under admin).
        abort 9001
    }

    /// Pure helpers for UIs/tests.
    public fun is_active(_g: &Grant): bool {
        // Step 1: Compare `_g.state` with S_ACTIVE; return true if equal.
        abort 9001
    }
    public fun state_of(_g: &Grant): vector<u8> {

    }
}
```

:::info Design choice
Keep transitions only in entry functions; never mutate `state` directly from other modules. This centralizes invariants and keeps tests focused.
:::

## Abilities audit (guided)

Tighten abilities to match intent and conservation rules.

- `AdminCap` and role tables should not be copyable; prefer only `key | store` where necessary.
|- `Grant` should not be copyable or silently droppable. Provide explicit burn/delete entry if destruction is allowed.
- If delete is allowed, decide who can delete and how indexes (e.g., `registry`) must be updated.
- Add asserts that enforce conservation (no duplicates; explicit ownership transfers).

## Tests: lock in rules

## Verification checklist

- Only admins can grant/revoke roles; issuer/revoker gates work.
- Pending → Active → Revoked enforced; illegal paths abort with named codes.
- Abilities align with intent (no accidental copy/drop on caps/resources).
- Tests cover positive/negative paths and any idempotent writes.

## Common pitfalls

:::caution
- Over‑permissive abilities on caps or grants → remove copy/drop.
- Single “status” without guards → enforce transitions in entries; never mutate `state` directly.
- No negative tests → add expected‑failure tests for each guard.
- Forgot index cleanup on delete → specify update order and assert post‑conditions in tests.
:::
